## 1. 项目目录结构要清晰。

整个项目的目录结构应该清晰，在项目构建时应考虑。包括：系统架构+技术架构+系统设计方案+实施计划+整个实施过程中的微调
整个项目所使用的模型要小一些，方便测试，尤其是本地，不代表线上。

## 2. 知识库的构建

1. 患者真实的医疗信息知识库（医院的所有患者的医疗记录）【可提升已存患者的回复的准确率，注意隐私】`构建知识图谱`
2. 通用的医疗信息知识库（针对所有的用户）

## 2.1 数据预处理相关问题。（做好预处理为文档切分、分词等后续提供高质量的输入）

### 2.0 数据清洗

- 对于数据集，比如：对话类的数据集作为知识库的话，我觉得可作为知识的首先是医生的回复，患者的问题还是要进行一些标准化之后可作为知识库，排除一些口语、非专业的术语等等。
- 清理乱码、广告水印、页眉页脚等，文本长度太短，或者描述模糊等数据，并且要对清洗后的数据质量进行检查，数据处理的不好，会影响后续一系列的动作，最终导致检索上的偏差。
- 对于医学上的特殊字符（单位符号：℃【摄氏度】、%【百分比】、【mg ⬆️ 】、检验符号【+代表阳性】等等），还是要酌情考虑。
- 一些专业数据的标准化（心梗-心肌梗死）、错别字、计量单位的标准化。
- 将结构化的数据转换成文本表达。（借助文本生成模型）
- 隐私数据的处理、知识产权
- 输出：格式统一成结构化文本（文本字符串）+元数据（json 格式）；图文要建立图和文的关联。小文本直接保存 json，大数据需要借助数据库。

### 2.1 哪些数据更适合作为知识库

- 诊断诊疗指南、专家论文、病例报告、正规教材等等。对于问答类的数据我觉得并不适合。

### 2.1 针对不同数据集需要有不同的处理机制。如：中文医疗对话数据集、VQA 数据集等。

#### 2.1.1 文本数据去重处理：

1. 数据量较大，确保内存不会溢出问题。
   单机：分块加载数据并处理，记录数据的唯一标识（哈希值、语义指纹），通过唯一标识去重。
   分布式：大数据架构 Sqprk/Flink，去重理念和单机一样。
1. 去重方案的选择问题：精准去重（完全相似【数据哈希】）、语义去重（判断向量之间的相似度【语义指纹】）、唯一 ID 去重（判断 ID 是否重复）
   唯一 ID 适合：数据库中存储的结构化数据。
   精准去重更适合：尽量保留数据，提升模型的性能，尤其是数据量少的情况。
   语义去重：适合数据量多的场景，如：文本数据。
1. 新增数据去重问题。
   需借助数据库，通过数据持久化进行新增数据的去重。

- 单机：LevelDB
- 集群：Redis
- 向量化数据库：Milvus/FAISS
- 大规模数据集：HBase

其实对于以上这些问题：编码实现太难了，门槛太高了。还是需要使用一些开源模型和工具。

- pdf、表格文本的加载和解析，模型 LayoutLM、TableTransformer（表格）

## 2.2 文档切分

目的：解决数据颗粒度的问题，能够进行高效检索。一篇 10000 字论文可能包含很多内容，我只想知道一部分，不切分整个论文都会匹配出来，切分后就能检索到相关内容，让检索更精准。而且切分后的检索效率高，计算量少。也能符合生成模型的输入文本的长度限制。

- 最好的是具有结构化的文本，像 markdown 文档，按照层级能够清晰保留语义。固定长度的切分很容易破坏语义关系。
- 语义很重要，而且对于垂直领域关联性比较强，医疗领域涉及发病机理，这种逻辑关系。比如：很多疾病是因为其他疾病所导致的、医学上的一些指标等等。（比如：口服某药物治疗，后面都跟着适用人群、用法用量、不良反应、禁忌等等）
- 切分还是要选择医疗上的一些专属的工具：MedCAT 或者 LangChain（RecursiveCharacterTextSplitter）+ 结合医疗关键词记性切分。还有就是可以做元数据标签，切分长度不要太小，以免破坏关联性。
- 文档的切分还要考虑到后面向量化模型的 token 限制。（一般要小一些，或者用分词向量化模型先进行测试一段文本切分 token 的数量）

## 2.3 分词相关问题。（中文、英文、垂直领域）

目的：拆分语义，让机器可读，为后续向量化提供“最小的计算单元”，模型的输入都是 token 序列，分词是模型处理之前必须做的。

### 2.3.1 对于分词如何进行选择？如何评估分词的效果？

本系统使用 jieba 分词。
1.jieba 分词比较轻量，适合小数据集。还应考虑垂直领域的自定义分词，如医疗领域：“心肌梗死”不能分为“心肌”和“梗死”。 2.分词效果的评估

- 使用公开的分词数据集进行评估。如：医疗分词标注集（公开）
- 人工抽取一部分数据进行评估。
- Henrychur/MMed-Llama-3-8B，多语言的文本分词模型 tokenizer

## 2.4 向量化相关问题。

目的：将文本转化为 “可检索的向量”，计算机可以进行计算的数字

### 2.4.1 图片向量化

图文数据集向量化：图片和文本应进行关联，且向量化的相似度应相似，处于同一特征空间，对于 rag 系统检索时，（文搜图、图搜文，才能正常匹配）。所以需要实现跨模态的向量存储。

### 2.4.2 语音向量化

- 间接向量化（语音 → 文本 → 向量）：医生的语音医嘱 “患者血压 130/80”→ 用间接向量化（转文本后生成向量，便于与电子病历文本匹配）；语音信号 → 语音识别（ASR）→ 文本 → 文本向量化模型 → 向量，对于语音识别的准确率要求比较高了。
- 直接向量化（语音 → 向量）：患者的呻吟声、呼吸声 → 用直接向量化（保留声学特征，辅助判断疼痛程度或呼吸状态）。

### 2.4.3 多种语言文向量化

- 使用多语言语义模型直接对齐多语言向量-paraphrase-multilingual-mpnet-base-v2、Henrychur/MMed-Llama-3-8B
- 翻译模型，将非中文翻译成中文，然后使用中文模型进行向量化，再通过中文向量化进行检索。
- 使用 Henrychur/MMed-Llama-3-8B 模型可以同时完成粉刺和向量化。
  - 能够系统系统效率，简化系统的链路
  - 适配医疗领域，能保障语义准确性
  - 多语言的向量化对齐，能够解决跨语言检索的核心痛点
  - 8B 的模型也比较小，开发和落地的成本不高

## 2.5 质量检查

目的：质量检查的核心目的是过滤低价值 / 无效数据（如空白文本、重复片段、乱码、无意义短句），避免这些数据进入向量库后，导致检索时 “召回无关结果” 或 “稀释有效信息”，最终影响 RAG 的回答质量。

- 完整性检查--过滤空白、长度异常的文本片段
  - 剔除纯空白 / 仅含标点的文本（strip()后长度为 0）；
  - 过滤过短片段（如小于 10 个字符，需结合业务调整，避免切分后只剩 “标题”“标点”）；
  - 过滤过长片段（如超过模型 Token 上限的 1.2 倍，避免后续向量化失败）。
  - 工具：Python 内置字符串方法
- 唯一性检查--剔除重复文本（避免向量库冗余）
  - 基于文本内容的哈希去重（如用 md5 生成文本哈希，对比去重）；
  - 基于语义相似度的去重（对短文本，用 Sentence-BERT 计算向量相似度，如相似度 > 0.95 则判定为重复，剔除其中一个）。
  - 工具：hashlib、sentence-transformers
- 相关性检查--过滤与业务无关的 “噪声文本”
  - 关键词过滤（如业务是 “医疗 RAG”，剔除含 “金融”“游戏” 等无关关键词的文本）；
  - 语义过滤（用轻量开源模型，如 DistilBERT，将文本分类为 “相关 / 无关”，仅保留相关文本）；
  - 乱码 / 低质量文本过滤（检查文本中特殊字符占比，如 > 30% 则判定为乱码，剔除）。
  - 工具：jieba（分词）、transformers（分类模型）
- 向量化前置检查--确保文本可正常转换为向量
  - 检查文本编码（统一为 UTF-8，避免因编码错误导致向量化崩溃）；
  - 预计算文本 Token 数（用向量化模型的 tokenizer 统计，如超过模型最大 Token 数，返回 “需重新切分” 提示）。
  - chardet（编码检测）、transformers（Tokenizer）

## 2.6 构建索引

目的：核心作用是存储文本向量 + 提供高效检索能力。索引构建的本质是 “将‘文本片段 - 向量’的映射关系存入向量化数据库，并建立检索索引”，让后续查询时能快速召回最相关的文本。

- 文本-向量-元数据(三元组)，将数据添加到 ChromaDB 并自动构建索引。
- 对于关键词索引（ES），知识图谱（Neo4j）
  - ES：有大量的结构化数据/半结构化数据，需要查询一些精确的信息数据，或者说需要支持过滤、排序、聚合查询等，再与向量化数据库结合，能提升精准度，从而来提高召回结果的准确性。
  - Neo4j：向量数据库无法裂解实体-关系，可通过 Neo4j 来弥补向量数据库的短板。

那需不需要使用 ES+Neo4j：
我得考虑：那比如我的多模态智能医生诊断系统来说（这个系统是针对某个医院而开发的），用户再输入问题的时候，可能会说去年怎么样、今年又怎么样，我需要了解用户在这个医院去年至今年的医疗信息，我觉得可以将医院关系型数据库的数据通过 ES 进行存储，但是这肯定是需要用户的唯一身份 ID 才能进行匹配，比如我的系统需要用户使用手机进行登录。那是不是说就可以 es+向量数据库相结合了呢？
还有，有些病症可能与家族史或者病理之间有关，那么我是不是可以构建这个用户的家族史的知识图谱 （Neo4j）以及病理之间的知识图谱（Neo4j）呢？这样再回复用户的问题时，再与向量数据库结合，准确率更高呢？
对于“医疗场景 RAG 系统” 的核心需求 —— 医疗诊断的准确性高度依赖 **“患者历史数据的精准匹配”（如历年就诊记录）和“结构化关联信息的深度融合”**（如家族病史、病理关联），而 “ES + 向量数据库 + Neo4j” 的组合，恰好能针对性解决这些需求，形成 “精准筛选 + 语义理解 + 关系推理” 的三重保障。

## 3. RAG 系统检索

## 3.1.向量检索

- 我觉得医疗系统检索的准确性要求是比较高的，采用 “向量化检索 + 关键词检索 + 知识图谱检索” 的混合检索模式，再配合重排序、阈值过滤等后处理步骤，是当前实现 “高质量数据召回” 的主流且高效的方案，尤其适配医疗场景对准确性、关联性的严苛要求。

## 3.2.重排序

- 重排序采用医疗逻辑权重 + 相似度分数，确保最终召回的 Top N 数据是 “对诊断最有价值的信息”。
- 医疗逻辑权重：第一优先级：用户本人的 “核心医疗记录”、第二优先级：知识图谱的 “强关联证据”、第三优先级：公共诊疗知识库的 “参考内容”。
- 相似度分数

## 3.3.阀值过滤

- 向量相似度阀值：低于 0.8 的直接过滤掉
- 数据有效性阈值：ES 陈旧病历，一些未验证的病理关系等等，需要过滤掉

## 3.4. 检索去重和文本摘要

- Falconsai_text_summarization
- 能够解决 “Token 超长” 问题，又能通过 “信息压缩” 降低大模型调用成本，同时还能提升生成回答的精准度。

## 4 用户输入处理

- 除了数据基本的处理之外，还需要更加规范化的处理（实体识别、意图识别、生成向量）
- 主要涉及系统的检索的准确性
  - 向量化检索：在文本预处理要强化医疗语义，医疗术语的标准化（“嗓子冒烟”=“咽喉黏膜充血”）时间维度结构化（3 个月前）
  - 关键词检索：关键词检索需要一些涉及隐私的数据，合规性还是要考虑的。用户查询本人数据：用户登陆后与医院数据关联，通过医院内部的 ID 进行查询。非本人查询的话，直系亲属并授权后进行查询。尽量多字段组合检索，准确率更高。
  - 知识图谱检索：一个是家族病史图谱、一个是病理关系图谱。

## 5.提示词（把模型当人来对待，你说的明白它生成的才明白，要精简，无废话）

- 角色和指令：明去大模型的身份和核心任务
- 检索上下文：检索的结果是大模型回答的唯一的依据
- 约束规则：规避医疗风险、数据安全风险、输出的边界（这个很关键）
- 用户的原始问题：明确需求，避免答非所问。

```python
def build_medical_prompt(patient_info, user_question, medical_records, family_history):
    """
    构建多模态智能医生诊断系统的提示词

    参数:
        patient_info: 患者信息字典，包含id_suffix, phone_suffix, hospital
        user_question: 用户原始问题字符串
        medical_records: 病历记录列表，每个元素是包含就诊信息的字典
        family_history: 家族病史信息字典

    返回:
        构建好的提示词字符串
    """
    # 构建患者基础信息部分
    patient_info_str = f"""## 一、用户基础信息（已脱敏）
- 患者标识：用户[身份证后4位{patient_info['id_suffix']}，手机号后4位{patient_info['phone_suffix']}]
- 目标医院：{patient_info['hospital']}（仅基于本院数据回复，不涉及其他医院信息）
- 当前时间：{patient_info['current_date']}
"""

    # 构建用户问题部分
    question_str = f"""## 二、用户原始问题
"{user_question}"
"""

    # 构建病历数据部分
    records_str = "## 三、精准检索到的本院医疗数据（核心信息提炼）\n### 1. 患者历史病历数据（摘要）\n"
    for record in medical_records:
        records_str += f"""- {record['date']}（{record['department']}）：
  - 主诉：{record['complaint']}
  - 检查结果：{record['examination']}
  - 诊断结论：{record['diagnosis']}
  - 用药方案：{record['medication']}
  - 医嘱：{record['advice']}\n
"""

    # 构建家族史部分
    family_history_str = f"""### 2. 家族史知识图谱关联数据（自然语言转化）
- 患者{family_history['relative_relation']}（身份证后4位{family_history['relative_id_suffix']}）于{family_history['diagnosis_date']}在本院{family_history['relative_department']}确诊"{family_history['disease']}"，目前{family_history['treatment']}
- 知识图谱病理关联：{family_history['pathology_relation']}
"""

    # 构建约束规则部分
    constraints_str = """## 四、回复约束规则（必须严格遵守）
1. 仅基于上述本院数据回答，不编造未提及的病历、用药、检查结果；
2. 避免绝对化表述（如不使用"肯定和糖尿病有关""吃这个药一定好"，改用"存在潜在关联""遵医嘱用药可缓解症状"）；
3. 输出需包含"问题回应、依据说明、用药回顾、就医建议、数据声明"5个模块，结构清晰；
4. 末尾必须加合规提示："以上内容基于本院历史医疗数据整理，仅作信息参考，不能替代医生面诊诊断及治疗方案，具体病情请以本院医生当面评估为准"；
5. 若涉及疾病关联分析，需结合现有数据客观分析，不夸大风险，也不遗漏关键提示。
"""

    # 构建输出格式要求部分
    format_requirements_str = """## 五、输出格式要求
请按以下模块分点回复，语言通俗（避免过多专业术语，若需使用需简单解释）：
1. 问题回应：直接解答用户核心疑问；
2. 依据说明：引用病历、家族史图谱数据，说明判断依据；
3. 用药回顾：清晰列出就诊的用药名称、用法用量；
4. 就医建议：针对用户情况给出具体、可操作的本院就医建议；
5. 数据声明：明确告知未查询到的相关数据；
6. 合规提示：严格按上述约束规则中的第4条完整呈现。
"""

    # 组合所有部分
    full_prompt = f"""你是{patient_info['hospital']}专属多模态智能医生诊断助手，仅基于用户在本院的医疗数据（病历、检查报告、家族史图谱）回答问题，核心定位是"辅助用户查询历史医疗信息、提供合规就医建议"，不替代医生面诊诊断。

{patient_info_str}
{question_str}
{records_str}
{family_history_str}
{constraints_str}
{format_requirements_str}
"""

    return full_prompt
```

## 9.智能体升级方案

使用 langchain 框架实现简单智能体：结合现有的 RAG 系统完整智能体，还需要的步骤：

1. 获取用户输入后，需要对用户的输入进行任务的拆分。-需要调用语义理解的模型，对任务进行拆分。得到子任务的列表。
2. 根据任务的拆分结果对任务进行规划，对于医疗的任务执行的顺序，我觉得需要丰富的医学知识（业务）或者一些医疗模型。
3. 对系统现有的模块封装成符合 MCP 协议的工具（比如：RAG 检索、ES 查询、知识图谱匹配），智能体自动调用最适合的工具。（还需要增加一些工具：用药指导、追问系统（问诊逻辑）、预约挂号等等）
4. 执行工具的调用，返回统一的结果格式。
5. 评估结果，根据评估的结果自我修正。所有的结果评估通过后构建提示词，生成回复。
6. 现有的 RAG 系统作为长期记忆，实现了医疗知识的存储，结构化病历可以使用 ES，交互历史就是让用户的对话历史进行保存（需要数据预处理）。那么短期记忆，LangChain 框架可实现，包括：本轮对话的内容，（用户输入、智能追问、中间结论（如：某个子任务得到的结果））、存储任务拆解的执行计划、存储任务拆解的子任务。

### 9.1 智能体架构设计

基于现有 RAG 系统，构建多模态医疗智能体，实现从被动问答到主动诊断辅助的升级。

#### 9.1.1 核心设计理念

- **任务导向**：将复杂医疗问题拆解为可执行的子任务
- **工具集成**：将现有模块封装为智能体可调用的工具
- **记忆管理**：结合长期记忆（知识库）和短期记忆（对话上下文）

### 9.4 高级智能体模式

#### 9.4.1 ReAct 智能体

**特点**：推理（Reasoning）+ 行动（Acting）循环

- 适用于需要多步推理的复杂医疗诊断
- 支持工具使用和结果验证的迭代过程

#### 9.4.2 Plan-and-Execute 智能体

**特点**：先制定详细计划，再执行具体任务

- 适用于需要系统性分析的医疗咨询
- 支持计划调整和动态优化

#### 9.4.3 Multi-Agent 系统

**特点**：多个专业智能体协作完成复杂任务

- **诊断智能体**：负责症状分析和初步诊断
- **用药智能体**：负责药物推荐和相互作用检查
- **护理智能体**：负责护理建议和康复指导
- **协调智能体**：负责任务分配和结果整合
